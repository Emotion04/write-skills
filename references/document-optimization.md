# 优化 Agent 文档（草稿）

> **状态：设计草稿，待讨论，未定稿。**
> 本文档是 write-skills 扩展功能的提案，供讨论方案的优劣，**不要求一次性写成定稿**。
> 讨论时请逐节质询：这一节的规则是否真的必要？是否可执行？是否与现有 skill 原则冲突？

优化任何供 Agent 消费的文档——AGENTS.md、CLAUDE.md、被指针引用的说明文档。目标：让文档只留"Agent 读代码/环境发现不了"的东西，防止堆积成屎山。

与写 skill 同一套底层原则（证据门槛、渐进披露、单点事实源），差别在**读者测试**——文档的价值是让 Agent 省一步，不是记录过程。

## 删减测试（每段必过）

对文档每一段问三个问题，任一"删"则删：

1. **能靠读代码/环境发现吗？** → 能则删（package.json scripts、目录树、--help 输出、配置）
2. **还准吗？** → 过期则删（写"当时环境"的段落，环境变了就误导 Agent）
3. **省 Agent 事吗？** → 不省则删（重复、铺垫、说教，让 Agent 多读一步）

一句话版：**"删掉这段，Agent 会不会做错？不会 → 删。"**

## 该写什么

- 环境查不到的：约定、决策原因、坑、边界、禁令（"为什么这样，不写就丢"）
- 环境查得到但 Agent 高频用、写下来省一步查询的：文件级命令（`pnpm vitest run -t "<name>"`，Agent 猜不到的）
- 防重犯错的约束：写约束不写描述（"永远 X / 绝不 Y / 当 X 则 Y"，不写"前端用了 Recharts"）

## 不写什么（可发现内容）

- `package.json` scripts 全文、构建/测试命令（`npm run` 一看便知）
- 目录树、代码结构描述（Agent 自己探索）
- linter/formatter 规则（配置文件已编码，"LLM 不是 linter"）
- 环境变量清单、依赖版本（.env.example / package.json 可读）
- 通用最佳实践、空泛指导（"写干净代码""记得提交前测试"）
- 操作流水账（见下节"过程 vs 结果"）

## 过程 vs 结果

日常小修复 AI 常把操作过程写进文档，但规范是**只留最终状态和"为什么"**：

- ✅ 留：最终状态（"现在用 pnpm"）、决策原因（"从 npm 换 pnpm，因为 workspace 慢"）、坑
- ❌ 删：操作流水账（先试了 npm i 报错、又试 yarn、最后装好——git log/git diff 能还原的）

判定一条"过程"要不要留，过三个测试：

1. **不可推断**：git log / git diff / 代码能还原吗？能 → 删
2. **有半衰期**：半年后还有用吗？只对当时有用 → 删
3. **防重犯错**：未来 Agent 不知道它就会重复踩坑吗？不会 → 删

流水账三条全挂 → 删。决策记录第 1 条能过 → 留。

业界成熟做法是 **ADR（Architecture Decision Record）**：只记"决策 + 原因 + 后果"，不记操作过程。

```markdown
# 决策：从 npm 换 pnpm

## 原因
npm workspace 在大仓库慢，pnpm 硬链接快 3 倍。

## 后果
- 新项目默认 pnpm
- 老项目仍用 npm，迁移成本高，暂不动
```

不写：安装报什么错、试过 yarn、花了多少时间——那些是流水账。

## 开发文档 vs 其他文档

文档不限于 CLAUDE.md。按读者分两类，但**当前不拆成两个文件**——两节共享"删减测试"，拆开反而制造重复。等某类内容膨胀到互相干扰，再拆不迟（渐进披露）。

- **开发文档**（AGENTS.md / CLAUDE.md）：让 Agent 改对代码。强调约束、命令、架构决策。
- **其他 Agent 文档**（手册/说明/规范）：让 Agent 执行/回答正确。强调任务标准、判断依据。

## 结构原则

- **渐进披露**：AGENTS.md 只放每次都要的硬约束 + 指针（~70-100 行），其余拆到按需加载的 docs
- **面包屑代替复制**：`见 src/repos/ 了解仓储模式`，不把内容抄进文档
- **单点事实源**：一条事实一处，相关材料用指针连
- **记录后置不预防**：Agent 犯错 → 你修 → 加一行坑。不提前写假设性问题（与写 skill 一致）
- **stale 比没有更糟**：文件过期会误导 Agent

## 与 instruction-audit.md 的关系

本文件复用 instruction-audit 的删减逻辑（重复/沉积/过期/散落），但**读者测试**是文档专属视角——写 skill 用"证据门槛"（保护约束/防失败），写文档用"读者测试"（省一步 vs 多读一步）。两者同源，不重复实现。

## 待讨论点（不要直接照做，先质询）

1. **读者测试 vs 证据门槛**：读者测试是否足够可执行？还是应该把证据门槛也显式引用进来，避免两套标准？
2. **命令到底写不写**：搜索结果有分歧——context-engineering 派说"别重复，用面包屑"，实用派说"写完整命令"。草稿折中为"只写文件级命令"，对吗？
3. **开发文档/其他文档分节**：两节共享删减测试合理吗？还是以后必然会各自膨胀，应该现在就拆？
4. **ADR 的引入**：要求 Agent 按 ADR 格式记录决策，会不会太重？普通文档场景适用吗？
5. **与 SKILL.md 的接缝**：SKILL.md 目前是"写 skill"定位。加入"优化文档"后，是加一行指针（本文档），还是需要在 SKILL.md 里调整触发/工作流？
6. **触发方式**：mattpocock 的 writing-for-agents 改成了模型自动触发（写 CLAUDE.md 时自动唤起）。你的 write-skills 是 `disable-model-invocation: true`（手动）。优化文档功能要不要模型触发？手动还是自动？
